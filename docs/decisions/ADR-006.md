# ADR-006: Sequencing — Vertical Slice vs Strict Phase 0 Gate
Date: 2026-10-10
Status: Proposed

## Context

The ROADMAP.md specifies a hard Phase 0 exit gate: "Do not proceed to Phase 1 until ALL of these are TRUE." This is a strict sequencing rule that prioritizes foundational understanding over early usability.

The session briefing (Section 8, PROPOSED) contains a competing proposal:

> "Sequencing: build a thin vertical slice first (Tier 0 + tools + morning brief on an API model) in parallel with Phase 0 fundamentals. This bends the 'Phase 0 exit gate, no exceptions' rule, so it needs an explicit ADR."

**Arguments for strict Phase 0 gate (current rule):**

1. Phase 0 foundational knowledge directly affects Phase 3 design quality. Not understanding EWC at the Fisher matrix level means poor λ choices and inability to diagnose sleep cycle failures.
2. Rushing to a vertical slice before understanding the components creates technical debt that compounds — specifically in MemMan (requires confidence calibration understanding) and the sleep cycle (requires EWC understanding).
3. The Phase 0 exit gate was designed precisely because "every hour of Phase 1 spent on something Phase 0 should have taught you costs 3 hours to unlearn" (PHASE0_GUIDE.md).

**Arguments for vertical slice in parallel:**

1. G1 (usable system early) is the highest-priority goal. Without daily-use feedback, the entire architecture is being designed in a vacuum.
2. A thin vertical slice (Tier 0 graph + 3 tools + morning brief) uses an API model (Claude/GPT-4), not the local Tier 1. It does not require EWC, QLoRA, or sleep cycle knowledge to build or use.
3. Daily use generates real correction events, preference data, and Tier 0 facts that will improve Phase 2 and 3 design decisions — without daily use, those decisions are hypothetical.
4. The vertical slice is structurally isolated from Phase 0 exercises: it can be built by Claude Code (not the owner) and does not require the owner to understand transformers or EWC to operate.
5. De-risks the project against owner context-switching: if Phase 0 takes 6 weeks of focused study without a working artifact, motivation risk is real.

**Objection I am registering (per standing rules):** The vertical slice proposal has a hidden risk that this ADR must name explicitly. If the API-backed thin slice works well, there is strong temptation to delay Phase 1 (local Tier 1) indefinitely — "the API version is good enough." This directly threatens G2 (persistent corrections) and G3 (evaluation rigor), which require local model weight control. The ADR must include an explicit tripwire: a date or milestone at which API-backed Tier 1 is declared temporary and local Tier 1 work begins regardless of comfort with the API version.

## Decision

PENDING: owner

Proposed resolution if owner chooses parallel: accept the vertical slice in parallel with Phase 0, with the following constraints:
1. Vertical slice code is owned and built by Claude Code — it does not consume owner's Phase 0 study hours.
2. Local Tier 1 work begins no later than Phase 0 exit gate completion, regardless of API version stability.
3. The API model used in the vertical slice is behind the same `FrozenCoreInterface` abstraction that will wrap the local model — making the swap a configuration change, not a refactor.

## Consequences

- If strict gate maintained: Phase 1 cannot start before Week 6. No working artifact until Week 12+.
- If parallel accepted: a usable system exists within 2 weeks; Phase 0 study proceeds in parallel on owner's schedule.

## Risks

- **API dependency creep:** Mitigated by FrozenCoreInterface abstraction and explicit local Tier 1 deadline.
- **Owner distraction:** Building the thin slice may pull owner attention from Phase 0 exercises. Mitigated by Claude Code owning the slice implementation.
- **Strict gate maintained:** Risk is low motivation and slow feedback loop for architecture decisions. Not a technical risk but a project survival risk.
