# ADR-004: Tier 0 Store — Neo4j vs RDFLib (Prototype Path)
Date: 2026-10-10
Status: Proposed

## Context

Tier 0 is the personal identity graph: the component that makes Veena personal rather than generic. It holds goals, projects, preferences, behavioral patterns, corrections, and relationships. It is written surgically and never consolidated away.

Two candidates for the persistence layer:

**Neo4j**
- Native property graph database; Cypher query language
- Production-grade: transactions, ACID guarantees, persistence, clustering
- Rich LangGraph integration via `langchain_community.graphs.Neo4jGraph`
- Complex schema changes require migration planning
- Requires running Docker container (or managed cloud instance)
- Learning curve: Cypher is not SQL; requires dedicated study
- ARCHITECTURE.md specifies Neo4j as the target (Section 2.2 schema is written in Cypher)

**RDFLib**
- Pure-Python in-process triple store
- No external service dependency; zero deployment friction
- SPARQL query language; direct mapping to semantic web standards
- Slower at scale; no ACID transactions; persistence is serialize/deserialize
- Easier to prototype with; harder to maintain at production data volume
- Schema flexibility higher (triples are inherently schemaless)

ARCHITECTURE.md already specifies Neo4j as the production target, and all Cypher queries in Section 2.4 are written for Neo4j. The question is whether to start with RDFLib as a prototype substrate and migrate, or go straight to Neo4j.

**Arguments for starting with Neo4j directly:**
- Avoids a migration that will touch every Tier 0 query in the codebase
- The schema is already written; no additional design work
- Neo4j local Docker setup is a Phase 0 exit gate item anyway

**Arguments for RDFLib prototype first:**
- Zero deployment friction lets the owner focus on schema correctness before ops
- Easier to iterate on the schema before it is production-committed
- RDFLib schema can be translated to Cypher mechanically once stable

## Consequences

- If Neo4j directly: commit to Docker dependency from first Tier 0 line of code; schema changes require Cypher migration scripts.
- If RDFLib → Neo4j: plan explicit migration milestone at Phase 3.5 start; ensure all Tier 0 query interfaces are abstracted behind a DAL so the store is swappable.

## Risks

- **Neo4j:** Schema rigidity is a tracked risk in ROADMAP.md. First schema version must be designed for extensibility.
- **RDFLib:** The prototype-to-production migration has historically been where projects stall. Budget an explicit migration sprint if this path is chosen, and do not let it slip past Phase 3.5 start.
